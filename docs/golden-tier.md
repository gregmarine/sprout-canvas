# Which tier hosts the golden-image suite

**Question R1 (PLAN.md §10.2).** Robolectric (fast, no device) or the instrumented tier? Settled by
measurement in Phase 2, as the plan required — not by preference.

**Answer: Robolectric, in `NATIVE` graphics mode.** The instrumented tier stays as a cross-check.

---

## What was measured

Both tiers render the **same 18 scenes**, defined once in
`canvas/src/goldenShared/kotlin/…/golden/GoldenScenes.kt` and compiled into both source sets. One
scene per pen plus the cases where a renderer has somewhere specific to go wrong: pressure ramps, a
translucent wash, single-sample taps, and a stroke that doubles back across itself.

| Tier | Runner | Where |
|---|---|---|
| JVM | `GoldenImageTest` (Robolectric, `@GraphicsMode(NATIVE)`) | `canvas/src/test/` |
| Device | `GoldenImageInstrumentedTest` | `canvas/src/androidTest/` |

Three properties had to hold before either tier could host anything:

1. **It renders at all.** Robolectric's *default* graphics mode records draw calls without executing
   them, so every bitmap comes back blank and a golden suite would pass forever while asserting
   nothing. `NATIVE` runs the real Skia pipeline.
2. **It is deterministic.** Rendering a scene twice must be byte-identical, or the suite is measuring
   the renderer's mood.
3. **It agrees with a real device.** Otherwise the committed goldens describe a JVM that no device
   matches.

## Result

- **Robolectric `NATIVE` renders correctly.** All 18 scenes draw; every pen is distinguishable;
  translucency, grain and the chisel nib all come out as intended. Two real bugs were caught during
  the measurement itself — a calligraphy nib with no thickness that drew *nothing* along its own
  angle, and grain coarse enough to read as dots rather than graphite.
- **Robolectric is byte-deterministic** across repeated renders in the same run and across runs.
- **It is fast.** The whole suite runs in the same JVM invocation as the rest of the unit tests, in
  seconds, with no device attached and nothing to install.

The instrumented tier can do everything the JVM tier can, and needs a device, an install, and a
connected fleet member to do it. Nothing about goldens requires hardware, so paying for hardware to
run them buys only the cross-check — which is worth having occasionally and not worth having on
every renderer change.

### Device comparison — the measurement

Run on a **Wacom Movink Pad 11 (DTHA116, API 34)** against goldens generated by Robolectric on
macOS/JDK 17, 2026-08-08:

```
scenes:     18
identical:  16
different:  2
missing:    0
worst per-channel delta: 1

  pen-highlighter:       194 px differ, worst channel delta 1
  colour-red-ballpoint:  277 px differ, worst channel delta 1
  …all 16 others identical
```

Sixteen of eighteen scenes are **byte-identical** across a JVM on a laptop and a real tablet's GPU-less
software canvas. The two that differ do so by **one unit on one channel** on a few hundred
anti-aliased edge pixels — rounding, not rendering. Both are translucent or coloured strokes, which
is where a fraction of an alpha unit has somewhere to land.

That is the answer to R1: for these renderers, Robolectric is not an approximation of a device, it is
the same Skia arriving at the same pixels.

`GoldenImageInstrumentedTest.reportDifferenceFromTheCommittedGoldens` is what produced that table. It
renders the identical scenes on a real device, compares them against the committed images, and
reports per-scene differences rather than asserting them. It writes the rendered PNGs and the summary
to the device's external files directory.

```sh
./gradlew :canvas:connectedDebugAndroidTest

# Gradle uninstalls the test APK when it finishes, so to read the report, install it and re-run
# the one test by hand:
adb install -r -t canvas/build/outputs/apk/androidTest/debug/canvas-debug-androidTest.apk
adb shell am instrument -w \
  -e class 'com.symmetricalpalmtree.sprout.canvas.golden.GoldenImageInstrumentedTest#reportDifferenceFromTheCommittedGoldens' \
  com.symmetricalpalmtree.sprout.canvas.test/androidx.test.runner.AndroidJUnitRunner
adb shell cat /sdcard/Android/data/com.symmetricalpalmtree.sprout.canvas.test/files/golden/comparison.txt
```

**Differences are reported, not asserted.** A device that anti-aliases an edge a shade differently is
not a regression in this library, and a red build for it would train people to ignore the suite. What
the instrumented tier *does* assert is the pair of properties that would make goldens meaningless
anywhere: every scene draws something, and rendering it twice is identical.

## What would change the answer

Re-run the comparison and revisit this if any of these happen:

- **Robolectric or its bundled Skia moves** and the JVM output stops matching devices. The
  instrumented comparison is how that gets noticed.
- **A renderer starts depending on something Robolectric fakes** — a hardware-only shader, a
  `RenderEffect`, anything that needs a GPU. Golden scenes deliberately render through a plain
  software `Canvas` today, which is also the branch an Onyx panel repaint uses.
- **The suite starts covering the view rather than the renderers.** Whole-view goldens would pull in
  layout, density and window insets, and those are far more environment-dependent than a stroke on a
  fixed-size bitmap.

## Running it

```sh
./gradlew goldenTest                                   # compare against the committed images
./gradlew goldenTest -Psprout.golden.regenerate=true    # accept the current rendering
./gradlew :canvas:connectedDebugAndroidTest             # cross-check on hardware
```

`goldenTest` is **not** part of `check`. Geometry assertions run on every build; pixels are looked at
deliberately, by someone who can tell a regression from an improvement (PLAN.md D13, §4.1.1).

Regeneration is a deliberate act with its own flag, and regenerated images are reviewed in the diff
like any other change. A golden that is regenerated reflexively whenever it fails is not a test, it
is a log.
